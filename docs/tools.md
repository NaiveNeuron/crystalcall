# CrystalCall tool surface

This document describes the **real** local tool families CrystalCall speculates
over, why each carries the effect annotation it does, how the immutable snapshot
identifiers are derived, how the SQLite read-only guarantee is enforced, and the
measured cold/warm durations frozen into `configs/tools.yml`.

Everything numeric below is generated by
`uv run scripts/build_snapshots.py --bench --emit-config configs/tools.yml --emit-docs docs/tools.md`
from `experiments/vendor/corpus/BENCH.json`. Nothing in this file is
hand-entered.

---

## 1. Why any of this exists

Speculative programmatic tool calling is only *lossless* if the value a
speculative execution produced is the value the authoritative execution would
have produced. CrystalCall does not try to detect that after the fact; it makes
it true by construction:

* a tool's value must be a pure function of **(canonical arguments, snapshot id)**;
* the snapshot must be **immutable** and **content-addressed**, so a changed
  snapshot is a changed identity rather than a silently different answer;
* tools whose value cannot be a function of a snapshot — anything that writes,
  or reads live mutable state — are **never** speculated, regardless of what
  the launch gate would like to do.

The tool surface therefore has exactly two kinds of member: speculation-eligible
`SnapshotRead` tools over a frozen corpus, and deliberately ineligible `Write` /
`LiveRead` tools that exist so the gate's abstention path is exercised by
something real rather than by a mock.

## 2. The frozen corpus

One staged corpus produces three snapshots plus one compiled kernel:

```
experiments/vendor/corpus/
  SNAPSHOT.json          composite  corpus@<sha256-16>
  repo/                  SNAPSHOT.json -> repo@<sha256-16>
  sqlite/corpus.db       SNAPSHOT.json -> sqlite:corpus@<sha256-16>
  embed/embeddings.f32   SNAPSHOT.json -> emb:corpus@<sha256-16>
  embed/ids.json
  bin/embed_search       deterministic CUDA kernel
  CORPUS_MANIFEST.json   ids, digests, counts, nvcc + ripgrep provenance
  BENCH.json             the measurements this document reports
```

Corpus inputs are chosen so a build needs **no network access** and is
deterministic for a given interpreter:

1. this repository's own `src/` and `docs/` trees (excluding `docs/tools.md`,
   which this build *generates* — including it would make the corpus id depend
   on the previous build's output and the pipeline would never converge), and
2. a fixed, sorted allow-list of CPython standard-library module sources located
   through `sysconfig` — `ast`, `json` and `sqlite3` among them, plus enough of
   `asyncio`, `email`, `encodings`, `lib2to3`, `multiprocessing`, `unittest`,
   `xml` and friends to clear the 300-file / 20 000-line floor.

The committed provenance record is `configs/corpus_sources.json` (with
`configs/corpus_sources.sha256`); the corpus itself lives under
`experiments/vendor/`, which is gitignored because it is ~540 MB.

### 2.1 Snapshot id derivation

The id is a pure function of content. For every snapshot kind:

```
entries  = sorted (name, sha256_hex(content)) pairs, ordered by name
manifest = canonical JSON {"kind": …, "entries": [[name, hash], …], "extra": {…}}
           (sorted keys, no whitespace, ensure_ascii=False)
digest   = sha256(manifest.encode("utf-8")).hexdigest()
id       = "<prefix>@" + digest[:16]
```

| kind | prefix | `name` | `extra` |
| --- | --- | --- | --- |
| repo | `repo` | POSIX path relative to the snapshot root | – |
| sqlite | `sqlite:<db stem>` | document path, hashed from `doc_meta` | schema version, database file name |
| embed | `emb:corpus` | `embeddings.f32`, `ids.json` | model id, dim, rows, window, dtype |
| corpus | `corpus` | `embed`, `repo`, `sqlite` | – |

Nothing derived from wall-clock time, hostname, inode numbers, file modes or
mtimes enters the digest, so two builds of identical content on different
machines produce the same id. Two properties this buys, both covered by
`tests/test_tools_snapshots.py`: the same content at two different filesystem
locations yields the *same* id, and changing one byte — or merely renaming a
file, since paths are hashed too — yields a *different* id.

The composite `corpus@…` id hashes the three sub-digests, so a rebuild of any
single sub-snapshot changes the corpus id. Each tool is nevertheless bound to
the id of the sub-snapshot it actually reads (`search_repo` and
`analyze_module` to `repo@…`, `sqlite_query` to `sqlite:corpus@…`,
`embed_search` to `emb:corpus@…`), so rebuilding the embedding matrix does not
invalidate cached `search_repo` identities.

Because the corpus contains this repository's own `src/`, the ids change
whenever the source tree changes. That is intentional — it is the same
mechanism that makes a stale speculation impossible — and it is why the
authoritative ids for a build live in `CORPUS_MANIFEST.json` rather than being
pasted into code.

### 2.2 Immutability enforcement

`build_*_snapshot` finishes by `chmod`-ing every file to `0444` and every
directory to `0555`, deepest first, and `verify_snapshot` recomputes the content
digest and raises `SnapshotDriftError` on any mismatch. Drift is fatal by
default rather than a warning: a snapshot that changed underneath a speculation
invalidates every equivalence claim built on it.

`uv run scripts/build_snapshots.py --verify` checks all four snapshots plus the
`0444`/`0555` permission invariant and exits non-zero if either fails.

## 3. The tools

### 3.1 `search_repo(query, path=".", max_results=50)` — `SnapshotRead`, `storage`

Literal (fixed-string) search for `query` inside the frozen repository snapshot
under `path`. Returns
`{"matches": [{"path", "line", "text"}], "engine": "ripgrep"|"python", …}`.

* **Effect: `SnapshotRead`.** It only reads a frozen, read-only tree; its value
  is a function of the query, the sub-path and the `repo@…` id.
* **Resource: `storage`.** The work is dominated by walking and reading the
  corpus, not by arithmetic.
* **Determinism.** Matches are sorted by `(path, line)` before truncation, so
  neither ripgrep's parallel traversal nor filesystem ordering can leak into the
  result. Match text is `rstrip`-ed of line endings and clipped to 400
  characters so result size is bounded. `--fixed-strings` is used (not regex)
  so the ripgrep and pure-Python engines agree on what a match is; the corpus is
  restricted to text suffixes for the same reason.
* **Engines.** ripgrep is resolved as `$CRYSTALCALL_RG` → `PATH` →
  `experiments/vendor/bin/rg` (a pinned static build; provenance, release URL
  and tarball sha256 are recorded in `configs/tools.yml` and
  `experiments/vendor/bin/PROVENANCE.json`). If no binary is found the tool
  falls back to a deterministic pure-Python scan and reports
  `"engine": "python"`. The engine actually used on this host is in the table
  below.
* **Containment.** `path` is canonicalised lexically against the snapshot root
  by `crystalcall.canonicalize`, and re-checked at execution time; anything
  resolving outside the root raises `PathEscapesSnapshot`.

### 3.2 `sqlite_query(database, sql, max_rows=100)` — `SnapshotRead`, `storage`

Runs one read-only `SELECT` against the frozen FTS5 index. Schema:
`docs(path, body)` (FTS5, `tokenize='unicode61'`) and
`doc_meta(path, sha256, lines, bytes)`.

* **Effect: `SnapshotRead`.** The database file is `0444` and opened
  immutable; no statement that could change it is allowed to run.
* **Resource: `storage`.** B-tree and FTS index reads.

**Read-only enforcement — four independent mechanisms, all of which must pass:**

1. **Connection URI.** `file:<path>?mode=ro&immutable=1`. `mode=ro` refuses
   write access at open time; `immutable=1` additionally promises SQLite the
   file cannot change, which suppresses locking and journal creation entirely.
2. **Single-statement check.** `sqlite3.complete_statement` is applied at every
   `;` boundary: if a complete statement ends before the end of the input, the
   string is multi-statement and rejected. `SELECT 1; DROP TABLE docs` cannot
   reach the database.
3. **Head allow-list.** After string literals, quoted identifiers and comments
   are blanked out, the first keyword must be `SELECT`. `WITH` is deliberately
   *not* allowed: SQLite accepts `WITH … INSERT`, so a `WITH` prefix is not
   proof of read-only intent.
4. **Forbidden-token scan + authorizer.** A word-boundary scan over the
   literal-stripped SQL rejects `INSERT`, `UPDATE`, `DELETE`, `REPLACE`, `DROP`,
   `ALTER`, `CREATE`, `ATTACH`, `DETACH`, `PRAGMA`, `VACUUM`, `REINDEX`,
   `BEGIN`, `COMMIT`, `ROLLBACK`, `SAVEPOINT`, `RELEASE`, `TRIGGER`, `ANALYZE`
   and `TRUNCATE`. Finally an `sqlite3` authorizer callback allows only
   `SQLITE_SELECT`, `SQLITE_READ`, `SQLITE_FUNCTION` and `SQLITE_RECURSIVE` and
   returns `SQLITE_DENY` for everything else — including any write or `PRAGMA`
   action a hand-crafted string might still smuggle past the text gates.

Because the scan runs on the literal-stripped text, `WHERE path LIKE '%insert%'`
is accepted (the keyword is inside a literal) while `SELECT 1 -- ok\n; DELETE …`
is rejected (the comment cannot hide the second statement).

**Determinism.** If the SQL contains an `ORDER BY`, rows are taken in the
query's own order and truncated to `max_rows`. If it does not, SQLite's row
order is not guaranteed, so all rows are fetched (up to a hard 100 000
row scan cap, above which the tool refuses and asks for an `ORDER BY`), sorted
canonically, and only then truncated. The result records
`"ordered_by_sql": true|false` so replay can tell which rule applied.

### 3.3 `analyze_module(path, checks=["syntax","complexity","imports"])` — `SnapshotRead`, `cpu`

Static analysis of one file in the frozen repo snapshot using **stdlib `ast`
only** — no external linter, no subprocess, no import of the analysed module.

* `syntax`: `{"valid": bool, "error": str|None}`; a `SyntaxError` is a result,
  not an exception.
* `complexity`: per function `{"name", "lineno", "branches"}` where `branches`
  is a cyclomatic-complexity-*style* count: `1` plus each `if`/`ifexp`/`for`/
  `while`/`except`/`with`/`assert`/`match_case` lexically inside the function,
  plus `len(values) - 1` for every `BoolOp`, plus `1 + len(ifs)` per
  comprehension clause. Nested functions and classes are counted as their own
  units, not folded into the parent. Names are qualified (`Widget.spin`) and
  sorted.
* `imports`: the sorted, de-duplicated set of imported dotted names, with
  relative imports keeping their leading dots.
* `counts`: `defs`, `classes`, `lines`.

* **Effect: `SnapshotRead`.** Pure function of the file's bytes; the id of the
  containing snapshot is what makes "the file's bytes" a well-defined thing.
* **Resource: `cpu`.** One small file read followed by pure parsing and tree
  walking.
* **Purity is tested directly:** the same bytes stored at a different path in a
  *different* snapshot produce an identical analysis (modulo the reported `path`
  and `snapshot_id`), and both equal `analyze_source()` on the in-memory string.

### 3.4 `embed_search(query, top_k=5)` — `SnapshotRead`, `gpu`

Dense retrieval over the frozen embedding snapshot. Returns
`{"hits": [{"id", "score"}], "device": "cuda"|"cpu", …}` with scores rounded to
6 decimal places.

**The snapshot.** `embeddings.f32` is a raw row-major `float32` blob of shape
`(rows, 768)` with L2-normalised rows, in sorted passage-id order, plus a
matching `ids.json`. A raw blob rather than `.npy` so the CUDA kernel can
`mmap` it with no header parsing and the numpy path can `memmap` the identical
bytes. Passages are `32`-token windows cut from each document at a stride
derived from the corpus token count (targeting `EMBED_TARGET_ROWS = 170_000`
rows), which sizes the matrix at a few hundred MB so one invocation is a real
accelerator load rather than pure launch overhead. Exact `rows`, `dim`,
`window`, byte count and stride-derived counts are recorded in the snapshot
metadata and in `CORPUS_MANIFEST.json`.

**The embedder is a documented pseudo-embedder, not a model.** Each token is
hashed with keyed BLAKE2b into a signed bucket (a signed random-projection /
"hashing trick" sketch), the ±1 counts are summed and L2-normalised, and the
result is cast to `float32`. It is exactly reproducible offline on any machine
with no download and no model weights, and it has **no semantic quality
guarantees whatsoever**. That is acceptable — and stated here loudly on
purpose — because this experiment is about **scheduling** a GPU-class retrieval op,
*not* retrieval quality. No claim
about retrieval accuracy is made anywhere in this project. The batched
construction is bit-identical to the per-token reference implementation
(`embed_text`) because summing signed integer counts in `float64` is exact.

**The GPU-vs-CPU decision.** `torch` is *not* installed in this project's
environment and deliberately stays uninstalled: a multi-GB CUDA wheel is a poor
dependency for a scheduling experiment, and on this box (`GB10`, `sm_121`,
CUDA 13.0) it would also compete for the same unified memory pool as the vLLM
server. Instead the GPU path is a standalone CUDA program,
`src/crystalcall/cuda/embed_search.cu`, compiled by `scripts/build_snapshots.py`
into `experiments/vendor/corpus/bin/embed_search`. A CPU-only numpy
implementation would not be enough: only real GPU work can compete with
DiffusionGemma denoising for the accelerator, which is the case the resource
gate must abstain on.

Determinism in the kernel is a hard requirement, so:

* exactly one CUDA thread per matrix row;
* each thread accumulates its 768 products in strict ascending index order into
  a single `float` register;
* no atomics, no split-K, no cub/thrust reductions, no warp shuffles, no tensor
  cores, no fast-math, and `--fmad=false` so the compiler may not contract
  `a*b+c` into an FMA (which would change rounding);
* top-k selection happens on the **host** over the returned score vector using
  a total order on `(-score, row index)`, so a tie can never reorder between
  runs.

Because GB10 shares one physical memory pool between host and device, a
concurrent vLLM server plus a full page cache can make the device allocation
transiently fail; the kernel retries the allocation a bounded number of times
and, on real exhaustion, reports the actual free/total bytes rather than a bare
"out of memory".

If the kernel is absent (no `nvcc`, compilation failed, or a non-CUDA host) the
tool falls back to a deterministic `float32` numpy `memmap` matmul over the same
bytes with the same `(-score, index)` ranking rule and reports
`"device": "cpu"`. The exact compile command, `nvcc` version and binary sha256
are recorded in `configs/tools.yml`, and the device actually used on this host
is in the table below. On the measured build the two paths agree on the
reported top-5 `(id, score)` pairs exactly.

### 3.5 Deliberately ineligible: `write_note` and `read_live_clock`

| tool | effect | why it can never be speculated |
| --- | --- | --- |
| `write_note(path, text)` | `Write` | Appends to a mutable scratch file. The side effect is externally visible, so executing it early is not a prediction — it is a commit. Even if the gate were certain the call will be made, launching it would reorder an observable write. |
| `read_live_clock()` | `LiveRead` | Reads the host wall clock. Its value is a function of *when* it runs, not of any snapshot, so a speculative value is simply a different answer. |

`EffectKind.speculation_eligible` is `True` only for `Pure` and `SnapshotRead`,
`ToolSpec` refuses a `snapshot_resolver` on any other effect, and
`EffectRegistry.is_speculation_eligible` is `False` for both tools above. Both
are fully implemented for the authoritative path — the gate abstains, it does
not lose the ability to call them. `write_note` writes only under
`$CRYSTALCALL_SCRATCH_DIR` (never inside a snapshot) and refuses to escape it.

### 3.6 BFCL-style `Pure` stubs

`build_impls` gives every `Pure` declaration a deterministic stub returning
`{"tool", "args", "ok", "canonical"}`, a pure function of the canonical
arguments with no filesystem, clock or network access. `build_impls` refuses to
invent an implementation for a non-`Pure` declaration, so an effectful tool can
never be silently faked.

For the deterministic-duration harness, `$CRYSTALCALL_TOOL_SLEEP_MS` injects an
interruptible sleep (`cancel.wait`) into those stubs. The variable is read at
call time so one process can sweep the 100/500/2000/5000 ms conditions; the
sleep does not participate in tool identity and cannot change a returned value —
both properties are covered by tests. A malformed value is a hard error, because
a silently ignored latency condition would corrupt every timing number in the
paper.

## 4. Measured durations

`expected_duration_ms` in `configs/tools.yml` is the **warm p50** of the fixed
benchmark workload below, and it is written by the generator, never by hand.

Cold rows drop the page cache **without `sudo`**: `os.sync()` followed by
`posix_fadvise(POSIX_FADV_DONTNEED)` over every file in all three snapshots,
plus a streaming read of a large unrelated file for additional cache pressure.
`fadvise` is the mechanism that actually works unprivileged, and the only one
that is meaningful on a 128 GB host where a global cache drop is neither
available nor reproducible. `/proc/sys/vm/drop_caches` is never written.
For `embed_search` the in-process id cache is cleared before each cold sample as
well.

### 4.1 Reading the table

* `search_repo` cold cost is dominated by re-reading the ~7 MB repo tree;
  `embed_search` cold cost is dominated by re-reading the ~540 MB matrix.
* `embed_search` is the slowest tool by a wide margin. Its warm cost is one
  process launch, one CUDA context creation and one host-to-device copy of the
  whole matrix. That is above the 50–250 ms band that would be ideal for a
  "small" GPU op, and it is the deliberate consequence of the matrix-size
  requirement: shrinking the matrix enough to reach 250 ms would drop it below
  the several-hundred-MB floor that makes the op a genuine accelerator load and
  a genuine competitor for the GPU. The size requirement wins; the measured
  number is reported as-is.
* `read_live_clock` is effectively free, which is exactly why it is a useful
  control: any observed benefit for it would be measurement error, not
  speculation.
